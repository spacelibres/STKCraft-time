# stkcraft-time 0.1.25

Release date: 2026-11-12

Kernel date literals now have an explicit resolver. A SPICE text kernel
may give an epoch as `EPOCH = @2000-JAN-01-12:00:00`; until this release
the crate had no public way to read that value, so a downstream reader
could only treat the text as a missing numeric constant.

## `kernel_date::parse_kernel_date`

```rust
use stkcraft_time::kernel_date::parse_kernel_date;

let epoch = parse_kernel_date("@2001-FEB-29")?;
assert_eq!(epoch.seconds_past_j2000, 36_676_800.0);
assert_eq!((epoch.year, epoch.month, epoch.day), (2001, 3, 1));
# Ok::<(), stkcraft_time::TimeError>(())
```

The result is N0067 TPARSE arithmetic: seconds past J2000 from
proleptic-Gregorian calendar fields. It is a bare kernel constant.

- No UTC, TT or TDB conversion is implied.
- No leap-second kernel is required, so `@1965-JUL-01` is an ordinary
  value and is not gated by `HistoricalUtcRequiresExplicitModel`.
- A day past the end of its month rolls forward; `@2001-FEB-29` is
  `2001-03-01`, matching native SPICE.
- The normalized calendar fields are returned alongside the numeric
  constant.

## Supported literal forms

| Form | Example |
|---|---|
| `Y-MON-D` / `Y-MM-D` | `@2000-JAN-01` |
| `D-MON-Y` | `@31-JAN-1987` |
| `MON-D-Y` with `-` or `/` | `@March-7-1987`, `@feb/4/1987` |
| Any of the above plus `HH:MM[:SS[.fff]]` | `@2000-JAN-01-12:00:00` |

A month may be a three-letter abbreviation or a full English name in any
case. Date fields must use one separator consistently; a mixture of `-`
and `/` is rejected.

## Explicit rejection

`TimeError::KernelDateUnsupported` is new. It is separate from
`LskMissing` and `SclkMissing` on purpose: a literal that is present but
unsupported must never be reported as an absent kernel variable, and it
must never be replaced by a default epoch.

Rejected forms include two-digit years (`@19-JAN-87`), ordinal
day-of-year (`@2000-060`), empty literals (`@`), and free text
(`@NOT_A_DATE`). Those are exactly the inputs native SPICE rejects with
`SPICE(BADTIMESPEC)`.

## Audit of existing readers

No other kernel reader silently converted a date. `parse_lsk` and
`SclkKernel::parse` already fail loudly on a non-numeric token. LSK
`DELTET/DELTA_AT` dates stay strict: an impossible calendar day is
`LskParse`, not a roll-forward, because a leap-second table with an
invalid date is bad data.

## Scope

This release does not claim complete TPARSE coverage. It covers the
literal forms in the native capture and rejects everything else
explicitly. STKCraft-Geocalc owns its own frame acceptance fixtures; this
release only provides the Time-side resolver.
