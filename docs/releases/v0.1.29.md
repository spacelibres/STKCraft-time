# stkcraft-time 0.1.29

Release date: 2026-11-12

Documentation-alignment release. There is no library, kernel-format or
numerical change; the parser, public signatures and every accepted value
are identical to 0.1.28.

## Why this release exists

Several documents still described the pre-0.1.28 behaviour. This release
makes the written contract match the shipped code.

| Location | Previous text | Corrected text |
|---|---|---|
| `README.md`, `docs/API.md`, `docs/TIME_CONTRACT.md` | implied `DD-MON-YY` | N0067 `TPARTV` token precedence |
| `docs/API.md` | month = abbreviation or full name | any prefix of at least three letters |
| `docs/API.md` | `HH:MM[:SS[.fff]]` | `HH[:MM[:SS]]`, decimal only in the final component |

| wiki `Home`, `Verification` | 0.1.26, 163/176 tests | 0.1.29, 165/178 tests |

## The precision point

Year selection is not a `DD-MON-YY` reading. An integer token of at least
1000 is a year; a year token in `0..=99` expands over the native
1969--2068 window. Therefore:

- `@31-JAN-1987` is 1987-01-31;
- `@19-JAN-87` is 2019-03-28, because token `19` is the year and token
  `87` is an out-of-range day that rolls forward.

That is how native SPICE resolves them, and the independent captures are
unchanged. Standalone `@2000-060` remains a native rejection. Full TPARSE
grammar conformance is still not claimed; see
`docs/reference/KERNEL_DATE_GRAMMAR.md`.
